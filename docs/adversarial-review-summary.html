Adversarial Test Review

Overview

This project generates end-to-end tests with machine-written code. This review is a second opinion on that output. Several AI reviewers work in sequence. Each has a narrow job and sees only some of the material. The goal is to find tests that would stay green while the system is broken, or fail on a correct system.

  • Reviewers run one after another, never in parallel.
  • The review is report only. It never edits tests, generators or generated files, never commits, and never pushes. Only its own run folder is written.
  • Every run writes to .adversarial-review/<timestamp>_test_<branch>/.

Sources: the adversarial-test-review skill, the agent definitions in .claude/agents/, scripts/adversarial-review-finalize.ts and scripts/adversarial-ui/server.ts.

Step 0

Trigger

  • From the command line: npm run generate-tests ends with an ## ADVERSARIAL REVIEW HANDOFF block. The repo's CLAUDE.md chains the review skill from it.
  • From the browser UI: run npm run adversarial-ui and open http://127.0.0.1:4173. The launcher starts claude -p in headless mode with a fixed list of allowed tools. The server does the preflight itself, so the headless run needs no approval for that step.
Why the UI showed "Do you want to approve that command?" A headless run has nobody to answer a permission prompt, so any tool call outside the allowed list stops it. Two read-only commands were added to the list: git blame and git branch --show-current.

Step 1

Preflight

Done by the main conversation plus one script.

  1. Check there is something to review. generated-tests/manifest.json must exist. If not, stop with "nothing to review - run npm run generate-tests first". This is a manual check, not part of the script.
  2. Choose the in-product reports. Use the handoff block's value, or on a manual run the newest report by folder name. Drop files that don't exist.
  3. Create the run folder .adversarial-review/{YYYYMMDD-HHMM}_test_{branch}/. The branch name comes from git branch --show-current, with / replaced by -.
  4. Extract the "blind-safe" inputs with npx tsx scripts/adversarial-review-finalize.ts blind-inputs {generated_dir} {run_dir}.
  5. Optionally fetch live sources (contracts and requirement text). This only happens when REGISTRY_API_URL and REGISTRY_TOKEN are set and point at a non-production stage. Otherwise sources is none.

What the script reads

generated-tests/manifest.json

Each test's entity. For conformance tests: source, contract id, content hash. For compat tests: the same three fields for publisher and consumer. For skipped entries: only the target, never the skip reason.

generated-tests/functional/manifest.json

The requirement ids from every plan, and the requirement from every skipped entry.

Output: requirements, contracts (id and hash), skipped contracts and entities, all sorted. The same data is saved as blind-inputs.json in the run folder. Finalize later uses it to detect whether the generated tests changed during the review.

The script does not validate the manifests, verify hashes or check counts, and a missing file is treated as empty.

Step 2

Pass 1: Blind reviewer

Agent adversarial-test-blind · tools: Read, Grep, Glob, Write (no shell) · model: fable

Job: work out what a correct test should check, without ever seeing the tests. This gives later passes an independent checklist.

May read

  • specs/active/odcs-contract-registry/requirements.md, design.md, acceptance-criteria.md
  • packages/core/src/api-map.ts, sources.ts
  • {run_dir}/sources/** (only if fetched)

Must never open

  • generated-tests/**
  • packages/testgen/**, packages/functest/**, packages/adversary/**
  • adversarial-reports/**
  • other files in .adversarial-review/

If it opens a forbidden file by accident, it writes only BLIND PASS COMPROMISED and finalize refuses to continue.

Output: expected-behaviours.md

  • Rows numbered X-01, X-02, and so on. The X- prefix is mandatory.
  • Each row has a side (consumer or generator), the behaviour a correct test must check, a verbatim quote and its location. A row without a quote is left out.
  • Sections: behaviours, generator obligations (R-80..R-93, R-115..R-126, R-117b, R-119b, section 3.12), information gaps, discarded embedded instructions.
  • For skipped contracts it writes what the skip must record.
  • Ends with PASS 1 DONE {count} items.

Live contracts: it reads contract content only if sources is set. Otherwise it knows ids and hashes only.

Step 3

Pass 2: Reconcile reviewer

Agent adversarial-test-reconcile · tools: Read, Grep, Glob, Bash (read-only), Write · model: fable

Job: attack the generated tests and the generator code, using the blind checklist as the yardstick.

Reads

  • expected-behaviours.md first, then everything under generated-tests/
  • Generator source: packages/testgen/src/**, packages/functest/src/**
  • packages/core/src/**, specs/**, each in-product report, and {run_dir}/sources/** if set

Shell (read-only)

git rev-parse --short HEAD, git log -1, npx vitest run <path> and node -e for counting. If node -e is denied once, it must not retry and should count with Grep instead.

Mandatory checks

#CheckRule
0Put every blind item X-nn in exactly one list: covered (with the file and line that checks it) or uncovered.AR-15
1Every functional plan's trigger path and read-back path must exist in API_MAP. Each unmapped path is its own Major finding.R-133e
2An assertion on a field absent from the asserting service's contract is Critical, even if the test never runs. With live sources, also check the live contract.R-133a
3Any number it states must be computed (Grep count or command output) and quoted, never estimated.-
4Name the applicable section 3.12 rule in the evidence.R-133a-e, R-134a-i, R-135, R-136

Free-form attack

  • Every generated test: would it pass against a broken system, or fail against a correct one? Is every field, value, env var, path and wait grounded in the contracts and the API map?
  • The generators: role assignment, ordering and determinism, cache keys, env-var handling, schema derivation, skip rules.
  • The in-product report: for each critic or deterministic finding (A-nn) it believes is wrong, add a "needs your decision" item. Don't repeat ones it agrees with.

Output: review.raw.json

Findings (severity, target file and line, defect, failure scenario, evidence), needs-decision items, covered and uncovered lists. It writes every candidate finding and drops none itself. Ends with PASS 2 DONE {count} findings.

Step 3b

Pass 3: Verify reviewer

Agent adversarial-finding-verify · tools: Read, Grep, Glob, Bash (read-only), Write · skipped only if Pass 2 found nothing

Job: try to disprove each finding against the real code. Pass 2 is another model and can be wrong.

  • Reads: review.raw.json and any repo file it needs: cited files in full, callers, tests, specs/**. It never reads expected-behaviours.md, so it stays independent of the blind pass.
  • Shell: git diff, git show, git log, git blame, git rev-parse, npx vitest run <path>.

For each finding, in order

  1. Open the cited code.
  2. Check the claim: is the quoted text real, and is the line number right?
  3. Try to refute the failure scenario: look for a guard, a validation, a caller that prevents it, an existing test, a spec sentence that makes it correct, or an input that cannot occur.
  4. Decide:
    • CONFIRMED: traced to the end and it holds, with a verbatim quote.
    • REFUTED: concrete counter-evidence found.
    • UNCLEAR: could not be traced, or depends on something not visible (live behaviour, requirement text). When in doubt, UNCLEAR.

Output: verification.json, with one entry per finding plus notes. It adds no findings. Ends with PASS 3 DONE {n} verified ({c} confirmed, {r} refuted, {u} unclear). If review.raw.json is edited afterwards, finalize ignores the older verification.

Step 4

Finalize

Deterministic script, no AI: npx tsx scripts/adversarial-review-finalize.ts finalize {run_dir}

Refuses to continue if

  • the blind pass is missing or compromised, or uses a prefix other than X-nn
  • the blind file was written after the reconcile pass
  • generated-tests changed since the preflight snapshot (AR-16)

Otherwise it

  • runs a citation audit (AR-18) and lists every reference that points at nothing under "Citations not verified"
  • shows Pass 3's verdict beside each finding (AR-19). Refuted findings stay in the table and still count in the verdict
  • applies the posture lint, assigns ids (F-nn, D-nn) and applies the verdict rule
  • accounts for every blind item, and reports any item Pass 2 skipped as "not assessed"
  • writes review.json, review.md and dropped.md (items the lint removed, with reasons)

Never hand-edit review.raw.json.

Step 5

Report to the user

  • The verdict line, the counts, the "needs your decision" items and the Critical findings (id, target, one-line defect).
  • The "Citations not verified" list and any refuted findings, since they affect how far to trust a finding.
  • Links to review.md (and dropped.md if anything was dropped).
  • No fixes, commits or snapshot restores unless the user asks.

Variant: adversarial-test-reconcile-update

  • Replaces steps 3 and 3b. One agent writes review.raw.json and then verification.json itself, refuting its own findings.
  • Not wired into any skill by default. The UI selects it with variant: 'update'.
  • Extra read-only commands: git diff, git show, git blame.
  • Trade-off: one agent instead of two, but its verification is not independent of the agent that raised the findings.

  • The -update verdict is FAIL partly because finalize counts its refuted Major. One confirmed Major remains (packages/adversary/src/mutate-testgen.ts:71).
  • Each agent was run once, so agent differences cannot be separated from run-to-run variation.
  • Both runs found the functional manifest had no plans (plans: []), so the unmapped-path and absent-field checks had nothing to run on.

Recommendation: use the standard chain as the default. Use -update as a second opinion and treat its findings as unverified until an independent Pass 3 checks them.

Known gaps

  • Preflight trusts the manifests and does not count or verify them. The blind pass said 171 requirement ids, but the manifest has 168.
  • With sources: none, neither the blind pass nor Pass 2 sees live contract fields or requirement text.
  • Nothing forces Pass 3 to cite the governing spec requirement or the contract schema.
  • The newest-report default can pick the wrong in-product report (the functest job's, not the testgen run's).
