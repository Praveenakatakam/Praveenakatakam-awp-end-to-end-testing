03 — WHAT HAPPENS AT EACH STEP

Phase by phase

The orchestrator is the main Claude session. It talks to you, launches the specialist agents and runs the gates. Agents can't ask you questions directly, so the orchestrator relays every assumption and open question to you.

00

Fit check orchestrator + you

Is this worth a spec?

  • Trivial change (typo, config tweak, one-liner)? Claude says so and offers to skip the process.
  • Anything bigger goes through a five-item checklist (fit-check.md).
  • If fewer than four items apply, Claude suggests a throwaway prototype first, so you learn before you specify.
OutcomeProceed with the process, prototype first, or skip it
01

Intake & gap discovery orchestrator + you

Surface what hasn't been thought through, before anything is written down.

  • Collects the idea, the user outcome, known constraints, and any security or breaking-change implications. If you named a stub, it starts from that.
  • Gap discovery: clarifying questions, most important first. These cover edge cases, requirements that could be read two ways (each reading stated), hidden assumptions, and production risks.
  • Claude doesn't ask what the codebase can answer. It looks it up and states it as an assumption you can correct.
  • Any question you can't answer yet becomes an Open Question in the spec.
OutputIntake notes, answers and stated assumptions, handed to the planner
02

Requirements planner · requirements mode

Write down exactly what "done" means, in testable language.

  • Writes requirements in EARS format, numbered R-01, R-02…, e.g. "WHEN the user clicks Export, the system SHALL…"
  • Adds non-functional requirements, an edge-case table, and a GIVEN / WHEN / THEN test outline for every requirement.
  • Returns its assumptions & ambiguities plus open questions tagged [BLOCKING] / [NON-BLOCKING].
  • Promotes the pending stub to specs/active/ if one was used.
Outputrequirements.md
GateYou resolve every [BLOCKING] question. The answers are written back into the spec before approval.
03

Analysis & design repo-analyst ∥ tool-analyst planner · design mode

Decide how, based on what already exists in the code and what's available off the shelf.

  • Two analysts run in parallel. repo-analyst finds existing patterns and reusable code. tool-analyst researches libraries and services for build-vs-buy.
  • The planner turns their findings into a design: architecture, data model, API surface, and integration boundaries.
  • Every significant choice shows the options and trade-offs, and is recorded as a decision (D-1, D-2…).
  • Every requirement maps to at least one component.
Outputdesign.md
GateFor each open question, Claude shows which decision resolved it and flags any resolution that was an assumption rather than a fact.
04

Task planning technical-planner

Break the design into small steps, each one reviewable in a single sitting.

  • Ordered tasks T-01, T-02…, each with Deps, Satisfies (requirement IDs) and Done when criteria.
  • Every task is paired with a test task: T-03 ↔ T-03a.
  • Each task has a named subagent (or "none, because…").
  • Tasks are grouped into phases. Phases run in order; independent tasks within a phase can run in parallel.
  • Every task traces to a requirement, which keeps out scope creep.
Outputtasks.md, the source of truth for progress
GateYou approve the plan
05

Adversarial review reviewer · pre-implementation

Find the holes in the plan while they're still cheap to fix.

  • Checks that every requirement has at least one task.
  • Checks that failure modes are handled, not just happy paths.
  • Flags missing test tasks, scope creep, and ambiguity: requirements two developers could read differently, unverified assumptions, open questions left unresolved.
  • Reports only real problems, not style nits.
OutputA short list of gaps, or "no blockers found"
GateBlocking issues are fixed in the spec before any code is written
06

Implementation, one task at a time test-writer implementer reviewer

Tests come from the spec, then code makes them pass. You see every change.

1 · DECLARE
Name the agent

Says which subagent will do the task, and proposes a split if the task is too big.

2 · TESTS FIRST
test-writer

Writes T-nna tests from the acceptance criteria and confirms they fail for the right reason.

3 · IMPLEMENT
implementer

Writes the smallest change that makes those tests pass. It never edits a test just to get it passing.

◆ 4 · GATE
You review the change

Summary of what changed. You approve before anything else happens.

5 · SYNC
Update the spec

Deviations or newly found edge cases go back into requirements/design with a D-n entry.

6 · REVIEW
reviewer

Post-implementation check for correctness, ACs and security, appended to review.md.

◆ 7 · GATE
You see the findings

Approve before the next task starts.

↻ NEXT
Next task

Repeat until the phase's tasks are done.

End of each phase: reviewer runs an alignment check (HC-1 & HC-2) on the requirements that phase covered, and every mismatch is reconciled before the next phase starts.
07

Health check & close-out /health-check tech-writer

Prove that spec, design, tests and code agree, then document what shipped.

  • Full health check (HC-1 to HC-5) across spec, design, tests and code. Every item is reconciled. Nothing is deferred.
  • UI work: Claude runs the app and checks the rendered result against the requirements. Passing DOM tests don't prove the layout works.
  • tech-writer updates the human docs (README.md, docs/), the agent reference docs (specs/docs/) and specs/registry.yaml.
OutputHealth report and updated docs, ready for your PR
GateYou approve before the spec is archived
04 — WHAT GETS PRODUCED

The spec folder

Each feature gets its own folder. These files are the feature's memory: they let any session, person or agent pick up the work.

specs/ ├── registry.yaml # index of every spec ├── pending/ # captured ideas (stubs) │ └── csv-export/ │ └── requirements.md ├── active/ # in progress │ └── csv-export/ │ ├── requirements.md # Phase 2 · R-nn │ ├── design.md # Phase 3 · D-n │ ├── tasks.md # Phase 4 · T-nn / T-nna │ └── review.md # Phase 6 findings └── archive/ # shipped
R-nn

Requirement. One testable EARS statement, e.g. "IF the export fails, the system SHALL show a retry option."

D-n

Decision. A design choice or spec change, with the options considered and the reason.

T-nn

Implementation task. Lists the requirements it satisfies and its "done when" criteria.

T-nna

Paired test task. Written before its T-nn, and always kept next to it in the plan.

HC-n

Health check. An alignment audit between spec, design, tests and code.

05 — WHERE DOCS LIVE

Two audiences, two places

Docs for people and docs for agents live in separate places and are written differently. Never mix them.

For people

Human docs

README.md + docs/
  • Overviews and getting-started guides
  • Architecture explanations
  • Diagrams in docs/diagrams/
Style: narrative and explanatory, written for teammates who are new to the area.
For agents

Agent reference docs

specs/docs/
  • System design, API surface, data model
  • Integration patterns (e.g. Bedrock, GitHub, Cognito)
  • The SDD process docs the agents follow
Style: terse lookup tables and reference files that agents read while they work.

Most features change both. tech-writer updates each one, in its own style, at close-out (Phase 07).

06 — THE TEAM

Specialised agents

Each agent has one job, reads only what it needs, and produces one deliverable. The orchestrator coordinates them and talks to you.

requirement-stubber
/stub-requirement

Captures an idea as a pending stub with minimal back-and-forth.

planner
phase 02 · phase 03

Writes EARS requirements, then the design with build/buy analysis and the decisions log.

repo-analyst
phase 03 · read-only

Finds existing patterns, reusable code and architectural constraints in the codebase.

tool-analyst
phase 03 · read-only

Researches external libraries, APIs and services, with pros and cons.

technical-planner
phase 04

Turns the design into ordered, paired tasks grouped into phases.

reviewer
phase 05 · 06 · health checks

Checks the plan before code, each task after code, and spec/code alignment.

test-writer
phase 06 · step 2

Writes tests from the spec before the code exists and confirms they fail correctly.

implementer
phase 06 · step 3

Makes the smallest change that passes the tests, then reports any deviation from the spec.

tech-writer
phase 07

Updates human docs, agent reference docs and the spec registry.

07 — GROUND RULES

What holds the process together

🧭

The spec is the oracle

When code and spec disagree, either fix the code or update the spec and record a D-n. A disagreement is never left unresolved.

🔦

Surface, don't assume

Every assumption, and every choice between readings of a requirement, is called out at the next gate.

🧪

Tests first, from the spec

Tests come from acceptance criteria, not from code. A test is never changed just to make it pass.

✋

You hold the pen

Claude stops at every gate and never commits. You review all the code and decide when it goes into git.

🧱

Small, traceable steps

One task is one reviewable change, and every task traces back to a requirement.

⏭️

Escape hatches, used once

"Skip review" or "skip tests" is honoured for that one task only, and the skip is noted in tasks.md.
